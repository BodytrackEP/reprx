# RepRx — Update Specification (Nov 2026)

You are working in the RepRx repository (hosted on Vercel, data in Supabase Postgres). Implement the changes below.

## Ground rules

1. **Inspect first.** Before changing anything, read the codebase and schema. Report back the framework, ORM/query layer, migration tooling, current tables for classes/programs/exercises/clients/overrides/RM tests/audit, how session weights are calculated (including rounding), and how print view is built. Then propose a phased plan mapped to the phases below and **wait for approval**.
2. All schema changes go in versioned migration files. No manual DB edits.
3. **Stop and confirm before any destructive step** (the RM data wipe in Phase 6, any table drop/rename).
4. Data stance is unchanged: RepRx holds client name + Cliniko patient ID only. No DOB, contact or clinical data. Override notes describe exercise changes only.
5. Anything that writes or edits programs, assignments, overrides, snapshots or RM results must write to the existing Audit log (old and new values, user, timestamp).
6. Programs are never hard-deleted. Archive only.
7. Practice timezone is **Australia/Brisbane** for all date logic (session dates, end-of-day lock).
8. Match the existing UI style (colours, amber override styling, components). Keep RLS/auth consistent with existing admin pages.
9. Update seed data so every new feature is demonstrable with the existing fake test clients.

## Phase 1 — Program Library with versioning (Items 2, 6)

### Behaviour
- New top-level nav item **Programs** (Program Library). Programs are standalone and reusable across classes.
- Program code is auto-generated: `PRG-0001`, `PRG-0002`, and so on.
- Structure stays as it is now: an ordered list of exercises with **sets (integer)**, **reps (text, max 20 chars, e.g. "10 SL", "8 each side")** and **% (numeric)**.
- Every save creates a new **immutable version**. The program points to its current version.
- Admin actions available to any admin: create, edit, **duplicate** (copy as a new program for rapid building), archive. No hard delete. Archived programs can't be assigned but remain visible in history.
- **Migration:** convert each existing per-class program into a library program. Merge programs that are identical (same exercises, order, sets, reps, %) into one, assigned to all the matching classes. Convert existing numeric reps to text.

### Class assignment and customisation
- A class has **one active program at a time**. Assignments carry `start_date` and `end_date` (nullable), and can be **future-dated** to queue next term. Enforce no overlap per class (e.g. exclusion constraint on a daterange).
- A class works from a class-level copy of the program's items, linked to the library. Each item has a stable identity key that persists across versions so items can be matched between versions.
- Admins can customise a class's copy: edit sets/reps/%, add rows, remove rows. Customised rows are flagged.
- **Push rule:** when a library program is saved, push the new version to every class with a current or future assignment of it.
  - Uncustomised rows take the new version (including exercise swaps, sets/reps/% changes, reorders, additions and removals).
  - **Customised rows are left as the class has them.**
  - Show a small "differs from library" indicator on customised rows.
  - Provide a "reset row to library" action.
- Audit every push (which classes and rows changed).

### Acceptance
- Two classes share one program. Editing a sets value in the library updates both, except a row one class has customised.
- Reps accepts "10 SL" and rejects 21+ chars. Grid header renders "3 × 10 SL @70%".
- Delete is unavailable. Archive works and hides the program from the assignment picker.

## Phase 2 — Supersets (Item 4)

- In the program builder (library and class copy), exercises can be grouped into a **superset of any number of exercises (2+)**.
- Grouped exercises must be **adjacent**. Provide **drag-to-reorder**, and grouping is only possible on contiguous rows.
- Sets/reps/% remain per exercise.
- Display as a **colour block** (distinct background or band per group) on the session grid and the **print view**. No A1/A2 labels.
- Superset membership is part of the program version and follows the same push rules as Phase 1.
- Client-specific exceptions are handled by overrides (Phase 4). No separate flag is needed.

## Phase 3 — Enrolment and program history (Item 3)

- Track **client ↔ class enrolment** with `start_date` and `end_date`. Moving a client between classes closes one enrolment and opens another. Never overwrite.
- Client program history is derived from enrolment periods overlapping class program assignments. It is **enrolment-based, not attendance-based**.
- History references the **program version** in effect, so it shows the program as it was then, not as edited later.
- **Client page:** a timeline listing program code, name, version, class, and from/to dates, with working weights drilled down from session snapshots (Phase 5).
- **Program page:** a reverse view of clients who have done this program, with dates and class.

## Phase 4 — Override notes and dormant overrides (Item 1)

- Overrides belong to the **client + exercise** and follow the client across classes and programs.
- Clicking a weight cell opens the override editor with **weight** and an optional **free-text note** describing the exercise change (e.g. "Trap bar instead"). No clinical content. Add helper text saying so.
- Cell display:
  - With a note, the cell shows the weight, and the **full note replaces the "Override" label**. The cell/row expands to fit; no truncation.
  - Without a note, the cell shows **only the weight**, with amber styling retained and no "Override" text.
- Notes appear on the **print view**.
- If an exercise is no longer in the client's current program, its override is **dormant**: kept, not shown, and it reactivates automatically if the exercise returns. Dormancy is derived, not a deletion.
- Audit create, edit and remove of overrides, including note text.
- Update the page footer text to match the new behaviour.

## Phase 5 — Session occurrences, frozen history, transposed grid (Items 5, 8)

### Session occurrences and snapshots
- Introduce **session occurrences** (class + date). The current `/admin/sessions/:id` is a class template; add a **date picker** to it.
  - Today or a future date shows a live calculation.
  - A past date shows the frozen snapshot.
- A snapshot stores, per enrolled client per exercise: exercise, position, superset group, sets, reps, %, calculated weight, override flag, override note, program version ID, and the RM result ID used.
- **Include all enrolled clients**, regardless of attendance.
- **Snapshot creation:** create the snapshot at whichever comes first, the **session start time** (scheduled job) or **staff first opening or printing** that occurrence.
  - Until the end of that day (Australia/Brisbane), the snapshot may refresh.
  - At **end of day it locks**.
  - For scheduling, prefer Supabase `pg_cron` or Vercel Cron. Check plan limits and report which you'll use.
  - The end-of-day job must also create any missing snapshots for that day's sessions before locking.
- **Past performance is never recalculated.** New RM tests, overrides or program edits affect only today (unlocked) and future sessions.
- Admins can **edit a locked snapshot** to correct errors. Every edit is audited with old and new values.

### Transposed grid
- Session grid layout:
  - **Clients across the top (columns)**, using **abbreviated names** (first name + surname initial, with the full name in a tooltip; disambiguate collisions).
  - **Exercises down the left (rows)**, showing name and sets × reps @%.
- The exercise column and client header row are sticky, and the grid scrolls horizontally.
- Supersets become colour-blocked **row groups**.
- Override notes wrap within the client column, and row height grows to fit.
- **Print view uses the same transposed layout**, landscape A4, including superset blocks and override notes.

## Phase 6 — RM Testing sessions and trend graph (Item 7)

### Model change
- RM tests are recorded as **Testing Sessions**: client, test date, auto-numbered per client (Session 1, 2, 3…), staff member who ran it, and session notes.
- A testing session contains many exercise results. **Each exercise can appear only once per session among non-voided results** (partial unique index). Voiding a result allows that exercise to be re-recorded in the same session.
- Result fields: exercise, reps (1–10), weight, est. 1RM (keep the existing Epley calculation, `weight × (1 + reps/30)`, with reps = 1 giving the weight itself), and void status with reason.
- Voiding is at the **individual result** level only.
- **Data:** wipe the existing RM test data and reseed with realistic multi-session data for the test clients (enough to trigger graphs for several exercises). **Confirm with me before running the wipe.**

### Graph and trend
- For a client + exercise with non-voided results in **3 or more testing sessions**:
  - Plot **est. 1RM per session** against the test date.
  - Overlay a **linear regression trend line**.
  - Show the trend slope (kg per week or per month) and the current trend-line estimate.
- Below the threshold, show a "needs 3 sessions" message instead.
- Voided results are excluded from graphs and calculations.
- Show the graph on both the **RM Testing page** and the **client page**.
- Use the charting library already in the project. If there is none, propose one before adding it.

### Program weights
- Session weights continue to use the **latest valid (non-voided) test result** per exercise, not the trend estimate.
- Keep the existing rounding logic.
